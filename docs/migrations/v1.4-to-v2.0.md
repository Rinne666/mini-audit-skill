# Migration: mini-audit v1.4 → v2.0

v2.0 is the Skill-First Refactor v2 (spec §1–§15). The two breaking changes for **delta authors** are:

1. **Spec §5 — Decision provenance is required for every semantic mutation.** Delta entries that change canonical state (assumptions_update status, blocked_paths_reopen, candidate_updates, etc.) must carry a `decision_id` and `decided_by` in the same delta's `decisions[]` field. The runtime refuses entries without them. See `schemas/research-delta.schema.json` for the new `Decision` shape.

2. **Spec §8 — `questions_add` / `intents_add` / `questions_resolve` collapsed into a single `research_intents_add` / `research_intents_update`.** The dual Question + Intent entity was redundant from a reasoning-ontology standpoint: one concept, one ledger row. The legacy fields are still accepted on the wire (routed to the same ledger kind) but new fixtures should use the merged form.

The third breaking change is internal to SKILL.md: it shrinks from 1389 to 805 lines. Methodology moved to `references/methodology/orchestration/`. The `references/README.md` link structure changed; the on-disk artifacts did not.

## Schema migration cheat sheet

### Before (v1.4)

```json
{
  "schema_version": 1,
  "questions_add": [
    {"key": "oq:sql-control-consumer", "question": "which mechanism consumes SQL control?",
     "priority": "P1", "related_capabilities": ["cap:sql"]}
  ],
  "intents_add": [
    {"key": "intent:sql-consumer-search", "question_ref": "oq:sql-control-consumer",
     "strategy": "capability-consumer-search", "priority": "P0"}
  ]
}
```

### After (v2.0)

```json
{
  "schema_version": 1,
  "research_intents_add": [
    {"key": "intent:sql-consumer-search",
     "question": "which mechanism consumes SQL control?",
     "strategy": "capability-consumer-search",
     "priority": "P0",
     "status": "open",
     "related": {"capabilities": ["cap:sql"]},
     "reason": "model decided to investigate the SQL-control consumer first"}
  ]
}
```

Note the changes:
- One entity instead of two.
- `question` is a required field of the entity (was previously hidden in `open_question.question`).
- `status` is required; default lifecycle starts at `open` (not `proposed`, which is reserved for an intent the orchestrator has already triaged).
- `related` is a free-form object (not the old `related_capabilities` array on `open_question`).
- `reason` is required: every research intent carries *why* it matters now.
- Updates use `research_intents_update` instead of `questions_resolve`; the field set is unified (no separate "resolution" verb).

### Decision provenance (new)

Any delta that writes to `assumptions_update`, `blocked_paths_reopen`, `candidate_updates`, or any other field that moves canonical state must include a `decisions[]` entry:

```json
{
  "schema_version": 1,
  "assumptions_update": [
    {"ref": "assumption:all-callers-coerce", "status": "disproved"}
  ],
  "decisions": [
    {"decision_id": "DEC-0007",
     "decided_by": "agent-L5-probe",
     "phase": "L5",
     "semantic_mutation": "assumption_judge",
     "reason": "the L5 probe traced all callers and found none coerce the parameter",
     "evidence_refs": ["src/foo.py:27", "src/bar.py:41"],
     "subject_ref": "assumption:all-callers-coerce"}
  ]
}
```

`decision_id` follows `DEC-NNNN` (4+ digits). `decided_by` may NOT be `runtime` or `system` (the runtime does not originate decisions; it records them). `semantic_mutation` must be one of the ten enum values:

```text
phase_complete_request
candidate_promote
candidate_reject
finding_confirm
finding_defer
blocked_path_reopen
assumption_judge
coverage_defer
research_intent_create
audit_stop
```

`audit_stop` is the only kind that allows an empty `evidence_refs` (the decision to stop the audit needs no supporting evidence). All other kinds require at least one entry.

### What stays the same

- Every other field of the delta (`facts_add`, `blocked_paths_add`, `capabilities_add`, `capabilities_update`, `edges_add`, `edges_update`, `blocked_paths_reopen`) is unchanged.
- The runtime CLI surface (`mini-audit-runtime <sub>...`) is unchanged. The new `mini-audit-runtime snapshot` and `mini-audit-runtime decisions` are additive.
- The search-ledger's `intents[]` and `open_questions[]` arrays still exist on disk. They are no longer the canonical write surface — `research_intents[]` is — but reads that target the legacy arrays continue to work (the runtime routes writes to the new array and migrates read paths to the new canonical form in a follow-up release).
- The `diff-scope.json` artifact is unchanged.

## CLI migration cheat sheet

- `--diff scope --since=<ref>` is unchanged.
- `--diff scope --commit=<sha>` (new in v1.4; unchanged) resolves to `<sha>^..<sha>`.
- `--diff scope --base=<x> --head=<y>` (new in v1.4; unchanged) resolves via `git merge-base`, **never** `base..head`.
- New: `mini-audit-runtime snapshot [--out PATH]` — read-only derived view; safe to call from any pipeline stage.

## Python-side migration

The Python runtime API in `runtime/research_state.py::apply_delta` accepts both the legacy fields (`questions_add`, `intents_add`, `questions_resolve`) and the new ones (`research_intents_add`, `research_intents_update`). Tests that previously wrote `intents_add` keep working but should migrate when convenient.

`runtime.research_state.LedgerSchemaError` is unchanged. The new `runtime.research_state.ResearchError` family covers decision-provenance refusals.

## Why this is necessary

Spec §8 says: *"If there is no clear need for one Question to be tracked under multiple independent strategies/owners/lifecycles simultaneously, prefer a single entity."* mini-audit's Question + Intent pair never had that need: every Question's lifecycle was determined by one Intent, and every Intent targeted one Question. The two-entity form was vestigial data modelling leaking into the agent's reasoning ontology.

Spec §5 says: *"Every semantic mutation of canonical state must carry a `decision_id` and `decided_by`."* Without provenance, an audit report's `findings.json` could not answer the question *"who decided this candidate is reportable?"*. The runtime auto-promotion we had in v1.4 (commit `0205446` ablation proof) was a *bypass* of this audit trail. Removing it was the point of v2.0.

## Timeline

| v1.4 (legacy) | v2.0 (current) | Removed in |
|---|---|---|
| `intents_add` / `questions_add` / `questions_resolve` | `research_intents_add` / `research_intents_update` | v3.0 (next major) |
| No `decisions[]` field | Required for semantic mutations | never (it is the audit trail) |
| `verdict: "search_saturated_under_current_budget"` (bare string) | `verdict: {kind: "derived.saturation_check", value: "floor_met", legacy_label: "..."}` (namespaced) | n/a (legacy_label kept) |
| `block_path.status` rewritten by runtime on assumption flip | `derived_events.append({event: "blocked_path_reopenable", ...})`; BP.status only moves on explicit `blocked_paths_reopen` | n/a (already done in v2.0) |
| `mini-audit-runtime lease run <task>` | Removed from `build_parser` (scheduler frozen → harness-owned) | n/a |
| SKILL.md 1389 lines | SKILL.md 805 lines (orchestration cookbook moved to `references/methodology/orchestration/`) | n/a |

python -m pytest tests/unit tests/invariants -q

python evals/incremental_run.py
python scripts/manifest.py --check
